# SwipeClean promo film — 2026-09-07

Motion-graphics promo built to five client-supplied Pinterest references.
Lives alongside, and does not touch, the July 2026 ad drafts documented in
`HANDOFF.md` (different brief, different style, pre-dates the green rebrand).

## Deliverables

| File | Spec |
|---|---|
| `renders/SwipeClean-promo-1080x1920.mp4` | 9:16 master — 30fps, H.264, 32.000s, **no audio track** |
| `renders/SwipeClean-promo-1920x1080.mp4` | 16:9 re-stage — 30fps, H.264, 32.000s, **no audio track** |

Both are re-stages of one timeline, not crops: `Promo.tsx` drives both
compositions from the same `SECTIONS` table, so the cuts cannot drift apart.

Delivered **silent by request**, cut to a fixed **120 BPM** grid (beat = 15
frames, bar = 60, film = 16 bars) so any 120 BPM track drops in without
re-timing. Remotion emits a silent AAC track on render; both files are stripped
with `ffmpeg -c:v copy -an`.

## Build order — THIS MATTERS

The film is a **two-pass render**. Pass one must complete first or the device's
screen renders blank:

```bash
# PASS 1 — the app UI, rendered to JPEG sequences that become screen textures
for c in ScreenSwipe:swipe ScreenSmartClean:smartclean ScreenCompress:compress ScreenStats:stats; do
  comp="${c%%:*}"; dir="${c##*:}"
  npx remotion render src/index.ts "$comp" "public/seq/$dir" \
    --sequence --image-format=jpeg --jpeg-quality=80 --scale=0.5 --frames=0-199
done

# PASS 2 — the film
npx remotion render src/index.ts PromoVertical  renders/SwipeClean-promo-1080x1920.mp4 --concurrency=3
npx remotion render src/index.ts PromoLandscape renders/SwipeClean-promo-1920x1080.mp4 --concurrency=3
```

`public/seq/` is ~56 MB of build input, not a deliverable.

## The device — three.js, not CSS

`src/promo/primitives/Phone3D.tsx`. Chosen from a four-way look-dev
(`src/promo/lookdev/`) after two CSS attempts were rejected.

CSS can fake depth in a still frame but cannot **relight** a surface as it turns
— a gradient is painted, not lit. The body is a real mesh under a Lightformer
studio rig, so the specular travels down the rail as the device rotates, which
is what the eye reads as solid.

**The root cause that broke every earlier attempt:** drei's
`<RoundedBox radius={r}>` **clamps r to half the smallest dimension**. On a
phone-thin box that is half the depth, so the corner radius silently became
under 5% of body width however large a radius was requested. Two look-dev
agents found this independently. Every front layer is now cut from the same
rounded profile — no flat rectangle is ever laid over a rounded body.

A photoreal GLTF is **not** needed and should not be added: the references are
stylised mockups, and moving light sells them, not polygon count.

### Staging — measured, not invented

95 frames across all 12 Moolah shots containing a phone were measured. The
rules, all of which an earlier build broke:

- **Zero roll.** |rotZ| ≤ 0.7° in every frame. A device leaning on a diagonal
  is the stock-mockup look the reference deliberately avoids.
- **Never exceeds 25°** of yaw.
- **Pitch is a frozen pedestal** per section (0, −8 or +2) held constant through
  the sweep. Animating pitch alongside yaw looks unstable.
- **Always mid-turn.** Not one reference shot holds a fixed angle; a frozen
  angle reads as a dead 3D render however well chosen.
- **~36° FOV.** Wider exaggerates the near/far edge difference and reads fake.

### The screen

A mesh cannot display React DOM, so the UI is rendered to JPEG sequences by
`ScreenComps.tsx` and loaded per frame with drei's `useTexture`.

**Video textures do not work here and should not be retried.** Both
`@remotion/three` video hooks are deprecated in 4.0.484 and neither resolves
during a render — verified by putting a magenta fallback on a bare full-frame
plane with the phone removed entirely; it stayed magenta.

The UI is drawn at **93% and centred** (`UI_INSET`) on the app's own background.
Full-bleed, its header and tab bar sat flush against the display border and the
display's rounded corners — 16.3% of screen width — cut into them, which is what
made the screens look oversized and cropped inside the phone.

## Transitions — liquid paint drips

`src/promo/primitives/LiquidWipe.tsx`, chosen from a three-way look-dev
(`src/promo/lookdev/wipes/`).

Matches the client's black-and-white matte pack recoloured per section. It is
**procedural SVG, not the supplied video**: a two-tone matte would normally be a
luma matte, but CSS `mask-image` does not accept video, and the brief was "same
thing, different colours" so it had to be recolourable anyway.

**No straight edge may ever be visible.** The rejected build drew a full-width
solid `<rect>` and swept its top edge — a flat horizontal line with colour
behind it. Here a body of paint hangs off the top of frame and pours down as
tapered runs (wide root → squeezed neck → heavy bulb) with droplets falling
ahead. There is no rectangle in the file; the only straight segments are parked
a full frame-height off-screen. Machine-verified across all 28 frames: worst
flat run 9% of frame width, typical 4–5%.

The **gooey filter is load-bearing** — blur, then slam the alpha back to a hard
edge so haloes fuse before outlines touch. Without it this is a bubble wipe.

`WIPE = 17` → a **34-frame (1.13s)** transition. It was 12 frames, which read as
instantaneous.

## Copy accuracy — read before changing a word

Every line was checked against the shipped app. These were caught and corrected
and **must not be reintroduced**:

| Rejected | Why |
|---|---|
| "Nothing leaves your phone." | False as a whole-app claim — the free tier links AdMob and RevenueCat, which transmit device and advertising identifiers. Now "Cleaning runs on your device.", which is true of the analysis. |
| "Half the size. **Same photo.**" | Reads as lossless. `store-listing-generated/LISTING.md` §6 permits "without visibly losing quality" and forbids upgrading it. |
| Smart Clean shown unbadged | It is Pro-gated (`feature-flags.ts`). Carries a PRO badge. |
| "Free on Google Play" | Implies every feature is free. Now "Get it on Google Play". |
| Invented detector counts | An early draft showed "241 screenshots · 1.2 GB". Fabricated. Only real figures from the supplied device screenshots appear. |

Also avoid: superlatives, competitor names, "AI-powered" (the detectors are MD5,
dHash and variance-of-Laplacian), "scans in seconds", and any iOS reference —
Android-only today.

The look-dev compositions are **deliberately not registered** in `Root.tsx`: a
background agent writing a variant file would otherwise break the film's bundle.
Re-register them temporarily if you want to compare variants again.

## Known limitations

- **No animation inside the glass beyond the baked sequences.** Sequences are
  200 frames; the longest scene is 195. A longer scene would hold its last
  screen frame rather than error.
- Fonts (Archivo Black, Inter) load from Google Fonts at render time, so a
  render needs network. Weights are pinned to keep this to a few requests.
- Render is slow — four WebGL scenes plus a texture load every frame.
- The device is shown in the **dark** theme, matching the supplied screenshots.
  `settings-service.ts` `defaultSettings` has `darkModeEnabled: false`, so a
  fresh install opens light. The film makes no claim about defaults, but do not
  caption it "what you get on install".
